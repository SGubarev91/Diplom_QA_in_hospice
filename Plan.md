# Этап 1. Ручное тестирование и проектирование тестов

## 1.1. Анализ границ приложения и функционала

Цель: зафиксировать, что именно реализовано в приложении «В хосписе», и очертить зоны, которые нужно
тестировать.

- **Основные экраны и навигация:**
    - экран авторизации;
    - главный экран;
    - список новостей;
    - карточка отдельной новости/события (заголовок, текст, дата);
    - раздел «Цитаты»;
    - меню (Главная/Новости);
    - лента всех новостей (сортировка, фильтрация, редактирование).
- **Типы данных и их отображение:**
    - текстовые поля (заголовки, описания, цитаты) — читаемость, отсутствие обрезания текста;
    - даты и время публикаций — корректный формат и локализация;
- **Зависимости и внешние условия:**
    - наличие интернет-соединения (загрузка новостей/цитат);

## 1.2. Определение типов тестирования

Для приложения с новостями и цитатами целесообразно применять следующие типы проверок:

- **Функциональное тестирование:**
    - загрузка и отображение списка новостей;
    - открытие карточки новости и проверка всех полей;
    - отображение цитат;
    - переходы между экранами и корректность возврата назад;
    - сортировка новостей;
    - фильтрация новостей.
- **UI/UX-тестирование:**
    - верстка и отображение;
    - читаемость шрифтов, контрастность, отсутствие наложений элементов;
    - работа скролла, отсутствие «залипаний».

- **Негативное тестирование:**
    - невалидные значения полей;
    - попытка отправки пустых форм;
    - некорректные действия пользователя (например, многократные клики, быстрый переход).
- **Тестирование стабильности и жизненного цикла:**
    - сворачивание/разворачивание приложения (сохранение состояния экрана и данных);
    - перезапуск приложения (корректная загрузка кэшированного контента или повторная загрузка);
    - возврат по кнопке «Назад» (корректное восстановление предыдущего экрана).
- **Манки-тестирование:**
    - хаотичные клики (ADB Monkey);
    - быстрые переходы между экранами с прерываниями;
    - сворачивание во время загрузки;
    - перезапуск приложения.
- **Сетевое тестирование:**
    - поведение приложения при отсутствии интернет-соединения;
    - восстановление работы после повторного подключения сети.

### 1.3. Составление чек-листа и тест-кейсов

- **Чек-лист (файл `Check` в формате XLSX):** список быстрых проверок с колонками: `ID`,
  `Область проверки`, `Описание проверки`, `Статус`, `Комментарий`, `Приоритет`.
- **Тест-кейсы (файл `Cases` в формате XLSX):** детальные сценарии с колонками: `TC_ID`,
  `Область проверки`, `Название`, `Предусловия`, `Шаги`, `Ожидаемый результат`,
  `Покрытие автотестом`, `Причина, если не покрыто`, `Приоритет` и `Статус`.

**Рекомендации:**

- Чек-лист использовать для быстрого ручного прогона.
- Тест-кейсы делать максимально однозначными, чтобы они могли стать основой для автоматизации.
- Сразу отмечать, какие кейсы планируется автоматизировать, а какие — нет, и почему.

---

### 1.4. Прогон вручную и фиксация результатов

1. **Подготовка среды:** установить приложение на эмулятор или устройство, авторизоваться (
   `login2` / `password2`), проверить наличие/отсутствие сети по необходимости.
2. **Прогон по чек-листу:** последовательно выполнить проверки, отметить статусы и комментарии.
3. **Документирование дефектов:** для каждого `Fail` зафиксировать шаги воспроизведения, ожидаемое и
   фактическое поведение, приложить скриншоты (можно получить через ADB) и логи (`adb logcat`).
4. **Актуализация тест-кейсов:** добавить новые сценарии, скорректировать предусловия и шаги при
   необходимости.

**Результат:**

- Обновлённый чек-лист с отметками статусов.
- Набор тест-кейсов с пометками о покрытии автотестами.
- Список дефектов с шагами воспроизведения и материалами (скриншоты, логи).

## Этап 2. Автоматизация проверки приложения

**Цель:** реализовать UI-тесты для ключевых сценариев, интегрировать Allure и подготовить данные для
отчёта.

### 2.1. Настройка проекта перед написанием UI-тестов

- Добавить директорию для тестов.
- Подключить необходимые библиотеки (Espresso).
- Настроить тестовый класс и базовый набор шагов (открытие экрана, ожидание элементов, клики,
  проверки).

### 2.2. Написание UI-тестов

- Реализовать автотесты для сценариев (TC_003, TC_004, TC_005, TC_006, TC_007, TC_008,
  TC_009, TC_010, TC_011, TC_014, TC_015, TC_016, TC_017, TC_018, TC_019, TC_020, TC_022, TC_023,
  TC_025, TC_026, TC_027, TC_028, TC_029, TC_030, TC_031, TC_033, TC_034, TC_039 и TC_041).
- Каждый тест должен завершаться проверкой (assert) результата.
- Учитывать нестабильные сценарии (сеть, таймауты) и либо исключать их из автоматизации, либо
  использовать заглушки.

### 2.3. Настройка сохранения APK на эмуляторе

- В файле `gradle.properties` добавить строку:
  ```properties
  android.injected.androidTest.leaveApksInstalledAfterRun=true
  ```

### 2.4. Интеграция Allure

- Подключить зависимости Allure.
- Разметить тесты: названия функциональностей, описания тестов, шаги.
- При падении теста сохранять скриншоты (через кастомный listener или утилиту).

**Результат:** набор автотестов, настроенная интеграция с Allure, готовность к формированию отчёта.

## Этап 3. Отчётность и сравнение эффективности

**Цель:** сформировать отчёт по результатам тестирования, сравнить эффективность ручного и
автоматизированного подходов, подготовить материалы для сдачи проекта.

### 3.1. Формирование отчётов Allure

- Выполнить прогон автотестов.
- Сгенерировать отчёт Allure.
- Скопировать содержимое папки allure-results и упаковать в архив allure-results.zip.

### 3.2. Сравнение времени ручного и автоматизированного тестирования

- Замерить время прогона чек-листа вручную (в минутах).
- Замерить суммарное время автотестов (включая сборку и запуск эмулятора).
- Оформить результаты в файле Result.md: количество сценариев, среднее время на сценарий, покрытие,
  факторы, влияющие на время.

### 3.3. Подготовка файлов для репозитория

- `Plan.md` — описание плана по проверке и автоматизации.
- `Check (XLSX)` — чек-лист с отметками о пройденных и непройденных тестах.
- `Cases (XLSX)` — таблица тест-кейсов с отметками о покрытии.
- `README.md` — инструкция по запуску автотестов.
- `allure-results.zip` — отчёт о результатах прогона тестов.
- `Result.md` — результат сравнения времени проверки вручную и UI-тестами.

## Этап 4. Инструменты. Устройства и эмуляторы. Интервальная оценка.

### 4.1. Инструменты тестирования:

- Android Studio + эмуляторы — среда разработки и набор эмуляторов с необходимой версией Android и
  конфигурацией.
- JUnit - раннер тестов, стандарт для Android‑тестов.
- ADB — для управления эмуляторами/устройствами, установки APK, снятия логов, просмотра экрана.
- Logcat / adb logcat — анализ логов приложения и системы для локализации ошибок.
- Espresso (Android) — для UI‑автотестов на Android. Выбран из‑за тесной интеграции с Android SDK.

### 4.2. Устройства и эмуляторы для тестирования:

- Смартфон Xiaomi 14T pro c API 36.0-ext22 (Физическое устройство).
- Pixel 10 Pro с API 36.1 (Эмулятор).
